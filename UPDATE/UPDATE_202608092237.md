## Why These Changes Were Necessary

### Why Model B Now Has Three Chronological Splits

Previously, the later meta-period was divided into Model B training and
validation only. Model B's checkpoint was selected using that validation tail.
Using the same tail again to select the gatekeeper threshold would tune two
decisions on the same observations and make the reported threshold look more
reliable than it really is.

The meta-period is now divided chronologically into:

- 60% for Model B fitting.
- 20% for Model B checkpoint selection and early stopping.
- 20% for threshold calibration only.
- An 84-sequence embargo between adjacent blocks.

The calibration tail does not train Model A, train Model B, or select either
model checkpoint. This separation is the main leakage-control boundary for
Phase 4.

### Why Model B Fits Only Eligible Signals

Model B is used only when Model A emits Buy or Sell. A Model A Hold prediction
cannot become a trade regardless of Model B's score. Training Model B on Hold
rows would give it many examples that do not match its live decision task and
could encourage it to learn signal occurrence rather than signal correctness.

Model B training and checkpoint validation now retain only Model A Buy/Sell
observations. The chronological boundaries are applied before this filtering,
so filtering cannot move future observations into an earlier split.

### Why the Threshold Is Not Assumed to Be 0.50

A neural-network softmax score is not automatically a calibrated probability.
The first smoke attempt demonstrated this: Model B's two-epoch scores were below
the original 0.40-to-0.90 search range, leaving no supported candidate.

The predeclared grid is now 0.05 through 0.95 in steps of 0.01. This does not
lower the reliability requirements. Every selected threshold must still:

- Accept at least 100 calibration signals.
- Retain at least 5% of Model A's eligible Buy/Sell signals.
- Match or improve the ungated Model A precision.

This treats Model B primarily as a ranking score while allowing the data-isolated
calibration tail to determine its usable operating point.

### Why Wilson-Bound Precision Selects the Threshold

Raw precision often favors extreme thresholds supported by only a handful of
trades. A threshold with one correct signal would report 100% precision even
though it provides almost no evidence of repeatability.

The selector maximizes the 95% Wilson lower confidence bound of accepted-signal
precision. The bound rewards precision but penalizes small samples. Minimum
accepted-signal and coverage constraints provide additional protection against a
nearly inactive strategy.

The report also records coverage, correct-signal recall, precision lift over
ungated Model A, and the complete threshold table so the decision is auditable.

### Why Trading Profit Does Not Select the Cutoff

Each threshold receives a validation-only trading simulation using the existing
TP, SL, time-stop, spread, and single-position rules. Net profit, drawdown,
Sharpe ratio, executed trades, and win rate are recorded for diagnosis.

Those trading results do not determine the selected threshold. Maximizing the
best historical profit across 91 candidates would overfit market noise and favor
the luckiest cutoff. The statistical reliability rule remains primary; trading
metrics are used to reject or investigate an economically unreasonable result
before the final test is unlocked.

### Why the Final Test Requires an Explicit Unlock

The old full-training path proceeded directly into the six-month test. That made
it easy to view final performance before reviewing and freezing the threshold.

A normal full run now stops after training, calibration, ONNX export, and report
generation. The locked final test is evaluated only when
`--unlock-final-test` is deliberately supplied. This makes accidental test-set
tuning substantially harder.

### Why Live and Backtest Load a Frozen Artifact

The selected production threshold will be written to
`threshold_calibration.json`. Both `live_execution.py` and
`backtest_simulator.py` load that same artifact and fall back to the configured
0.52 default only when no production calibration exists.

This avoids copying the chosen number into multiple files and prevents live and
backtest behavior from silently diverging. Smoke artifacts are written under
`outputs/smoke`, so the live process cannot load the diagnostic threshold.

## Implemented Files

- `threshold_calibration.py`: deterministic threshold grid, Wilson lower bound,
  eligibility/coverage constraints, selection, and audit results.
- `strategy_config.py`: fixed calibration policy and frozen-threshold loader.
- `gemini-training.py`: three-way purged Model B split, eligible-signal fitting,
  calibration inference, JSON/CSV reports, trading diagnostics, and final-test
  lock.
- `live_execution.py`: loads the frozen production threshold.
- `backtest_simulator.py`: uses the same frozen threshold and comparison rule.
- `training_runner.py`: can pass the explicit final-test unlock when Phase 6 is
  authorized.
- `tests/test_threshold_calibration.py`: statistical selection, grid, artifact
  loading, eligibility, and anti-profit-chasing tests.

## Generated Calibration Artifacts

A production full run will create:

- `threshold_calibration.json`: selected cutoff, rule, constraints, period,
  selected metrics, and all candidate results.
- `threshold_calibration.csv`: flattened threshold-by-threshold audit table.
- `outputs/model_metadata.json`: split dates and the selected threshold summary.

Smoke versions remain under `outputs/smoke` and are ignored by Git.
