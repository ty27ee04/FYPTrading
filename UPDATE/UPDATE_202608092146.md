# Engineering Update: WSL CUDA Training Readiness and Smoke Validation

**Recorded:** 2026-08-09 21:46:59 (UTC+08:00)

## Summary

This update completes the training-readiness block following the leakage-safe
dataset and classification-pipeline work. A project-local WSL environment was
created, CUDA access was verified, preprocessing-only and smoke-training modes
were added, and the classifier pipeline completed a short end-to-end GPU test
without evaluating the locked final-test performance.

## Why These Changes Were Necessary

The purpose of this block was not to improve the reported model score directly.
It was to make future training results trustworthy, repeatable, safe to deploy,
and inexpensive to monitor.

### Why WSL and CUDA Were Configured

The classification pipeline performs repeated CNN, LSTM, attention, and TCN
training over approximately 100,000 sequences. Running this workload on the CPU
would substantially increase experiment time and make threshold/model iteration
impractical. WSL already had access to the RTX 4060 through the Windows NVIDIA
driver, so it provides an appropriate Linux training environment without changing
the Windows-based MetaTrader5 execution environment.

Training and live execution remain separated deliberately:

- WSL is responsible for preprocessing, training, backtesting, and ONNX export.
- Windows remains responsible for MetaTrader5 connectivity and live execution.

This keeps the GPU training stack independent from the broker terminal while
still producing portable ONNX artifacts for Windows.

### Why a Dedicated Virtual Environment Was Added

Machine-learning libraries have tightly coupled binary dependencies, especially
PyTorch, CUDA, ONNX, NumPy, and ONNX Runtime. Installing them into a general system
Python environment could break unrelated applications or make the experiment
impossible to reproduce.

The `.venv-wsl` environment isolates the project dependencies. The generated
package lock records the exact versions that completed the smoke test, allowing
the successful environment to be reconstructed or audited later.

### Why Preprocessing-Only Mode Was Added

The original script immediately proceeded from loading data into expensive model
optimization and training. That made it difficult to detect a bad split, class
imbalance, feature failure, or leakage before spending significant computation.

`--preprocess-only` provides a cheap validation gate. It confirms dataset
boundaries, feature generation, scaler behavior, split sizes, dates, and class
balance before any model is optimized. A failed preprocessing check now stops the
workflow before producing misleading model artifacts.

### Why the Final-Test Labels Stay Locked

Repeatedly viewing final-test accuracy while changing hyperparameters, class
weights, thresholds, or features turns the test set into another validation set.
The resulting score would no longer represent genuinely unseen performance.

The preprocessing and smoke modes therefore report only the final-test date range
and number of sequences. They do not print its class distribution, predictions,
classification report, or trading performance. The final test should be opened
only once after all model and threshold decisions are frozen.

### Why Split Dates and Class Balance Are Reported

Chronological split counts alone are insufficient for a trading model. The report
includes exact boundaries so reviewers can verify that each period occurs after
the preceding period and that embargo gaps exist between them.

Class distributions are reported for development periods because severe
Buy/Hold/Sell imbalance can cause a model to achieve deceptively good aggregate
accuracy by predicting the dominant class. The observed development distributions
are reasonably balanced, although class weighting still needs validation rather
than being accepted automatically.

### Why Smoke-Training Mode Was Added

A full 30-trial, 100-epoch workflow is too expensive to use for discovering basic
integration errors. `--smoke-test` intentionally runs only enough work to prove
that:

- Optuna can create and finish a trial.
- Model A can train, validate, and save a checkpoint.
- Held-out Model A predictions can generate Model B labels.
- Model B can train and validate without invalid losses.
- Both models produce the expected output dimensions.
- Both models can be exported to ONNX.

Smoke losses are not used to judge strategy quality because two epochs are not
enough to produce a final model.

### Why Model B Uses a Later Held-Out Period

Model B is intended to estimate whether Model A is likely to be correct. If its
labels are generated from samples used to train Model A, Model A's in-sample
success will make the gatekeeper appear more reliable than it is.

Generating correctness labels from a later period unseen during Model A fitting
reduces this optimism. Giving Model B its own later validation tail also prevents
its checkpoint and early stopping from being selected using training loss.

### Why ONNX Runtime Validation Was Added

Successfully writing an ONNX file does not guarantee that the file is structurally
valid, loadable by the runtime, or compatible with the expected input and output
shapes. Exporter differences can also appear after a PyTorch upgrade.

Each exported model is now checked by the ONNX structural checker and loaded by
ONNX Runtime for a real inference call. Model A must return shape `(1, 3)` and
Model B must return shape `(1, 2)`. This catches deployment incompatibilities
before an artifact reaches the Windows live system.

The smoke run initially identified that current PyTorch requires `onnxscript` for
its exporter. Adding it to the dependency definition turned that discovery into a
repeatable environment requirement.

### Why Smoke Artifacts Are Isolated

A smoke model has seen only two epochs and must never be mistaken for a production
model. Using the same filenames as live artifacts could allow `live_execution.py`
to load a smoke checkpoint accidentally.

All preprocessing-only and smoke outputs are therefore written under
`outputs/smoke`. Production filenames at the repository root are reserved for a
deliberate full training run. This is a deployment safety boundary, not merely a
file-organization preference.

### Why the Local Training Runner Was Added

Long GPU training does not need continuous Codex involvement. Frequent agent
polling would consume additional credits without improving the local computation.

`training_runner.py` lets the GPU job run independently while recording a durable
log and a small status file. Codex only needs to inspect a completed or failed
state, reducing credit usage while preserving enough evidence to diagnose a
failure.

### Why Full Training Has Not Started Yet

The current gatekeeper threshold of 0.52 is still provisional. Starting final
training and opening the test report before defining the threshold-selection
method would encourage decisions based on final-test performance.

Validation-only threshold calibration is therefore the next step. Once the
threshold-selection criteria and strategy settings are frozen, full training can
run locally and the final six-month test can be evaluated once.

## New Training Controls

`gemini-training.py` now supports:

```text
--preprocess-only
--smoke-test
--optuna-trials N
--model-a-epochs N
--model-b-epochs N
```

The preprocessing-only mode validates the datasets, generates features and
chronological splits, reports development-period class balance, writes metadata,
and exits before optimization or model training.

The smoke-test mode forces:

- One seeded Optuna trial.
- One short Optuna training epoch.
- Two Model A epochs.
- Two Model B epochs.
- Held-out meta-period inference validation.
- ONNX export and runtime validation.
- No final-test classification report or backtest.

## Artifact Isolation

Preprocessing-only and smoke modes now write model/scaler artifacts under
`outputs/smoke`. They cannot overwrite or impersonate the production files
loaded by `live_execution.py`.

Production artifact names at the repository root are reserved for a deliberate
full training run. Current smoke artifacts are ignored by Git and must not be
used for live or paper trading.

## Local Status Monitoring

Added `training_runner.py`, which:

- Runs preprocessing, smoke, or full training using the active Python runtime.
- Streams output to `outputs/training.log`.
- Writes `outputs/training-status.json` with running, completed, or failed state.
- Records the process ID, command, return code, and update time.

This allows long training to run locally without frequent Codex polling.
